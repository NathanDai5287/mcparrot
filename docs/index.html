What exists today

When the local workspace is running, you can open the local workspace in your browser. The workspace uses the Calm design. In it, you can create a website app, add a draft task, and open the teaching preview of that task. Draft tasks cannot run yet, and the preview does not open the real website or record your actions. The main workspace does not yet support sign-in, task execution, assistant connections, or sign-in recovery.

The finished product will run website browsers in the background, without opening a separate browser window. You enter sign-in details and verification codes in our app for supported websites. We still need to choose how you demonstrate tasks. The hosted product remains planned.

You can open the local sign-in test while it is running. It uses a hidden browser on your computer, without Cloud credits or an AI model. Your password and code pass directly to that browser; this test does not save them. The browser keeps its signed-in session.

The Berkeley test completed school sign-in, SMS verification, and Canvas access. Access remained available after a page refresh. We then added the observed verification steps to the test flow, but have not repeated the complete automatic flow from a fresh session. This school-specific test does not record tasks, repeat website requests, or provide an assistant connection.

You can also compare the three earlier designs, which use sample data.

Where the app runs

The website has a Vercel project on the existing free Hobby plan. It is connected to our public GitHub repository. Updates to the main version start a production deployment. Other branches receive preview links. We still need to check the first published version.

Today, the website is a dashboard preview. It does not need a database, because changes disappear when you refresh. The school sign-in test stays on your computer. The public dashboard cannot control that test or access its saved sign-in.

A hidden browser must stay available while you complete phone verification. Vercel handles short requests, so that browser needs a separate host. Passwords, browser profiles, and private website content stay outside the public deployment. These HTML guides also remain separate from the website.

How the product works

You create an app for one website, then teach that app several tasks. Your assistant, such as ChatGPT, then uses all the tasks of a website app through one MCP connection. MCP is a standard way for an assistant to find and use the tools that you saved in another app, and each task you teach becomes one of those tools. Canvas, the course website of your school, is our first example, but the product is intended for many websites.

Teaching a website task

This is the planned teaching experience. Today, the workspace shows only a preview of it.

  1. Create your app

    Visit our website, select Create app, and enter the website address. For example, name the app “Canvas.”

  2. Sign in yourself

    Open the browser view and sign in to your school account. Complete Duo or any other verification that the school requires.

  3. Start recording

    Select Create task, name the task, and start recording. Then do the task in the browser. The app records your clicks and the messages that the website sends and receives behind the page.

  4. Review what can change

    Stop recording when you reach the result. Review the task and select the inputs that can change, such as a course or date range.

  5. Test and enable the tool

    Test the task with different inputs and check the result. The app tries to repeat the website messages without clicking through the pages. Enable the tool after that test succeeds.

  6. Add more tasks

    Teach other tasks inside the same app. You keep one website connection with several enabled tools.

You are the teacher

By default, you demonstrate each task yourself. Browser Use gives the browser access, and later it will also help you sign in again. We also plan to let an agent that you authorize use the same teaching session.

Using your assistant

This is the planned experience after you teach a task.

  1. Connect once

    Add the MCP address of your app to a compatible assistant, such as ChatGPT where it is supported.

  2. Ask for a result

    “Find my assignments due this week.”

    Your assistant chooses an enabled tool and supplies its inputs.

  3. Get the result

    The app repeats the saved website messages with your active login. Your assistant receives the result, and nobody needs to click through the website pages again.

Your assistant can combine the tools you taught to answer new requests. In the first version, an action that you have never taught needs another demonstration. Some actions may still need browser steps, and we must test and support those steps before we enable their tools.

Two kinds of connections

Each website app will get its own connection, and MCP Anything will get a separate management connection. Neither kind is available yet.

YouTubeRun the verified tasks you taught inside your YouTube app.

For example, a Canvas app and a YouTube app give you two website connections, and the management connection makes three in total. Each website connection includes all the enabled tasks of that app, so you do not connect each task separately. You need the management connection only if you want your assistant to manage MCP Anything for you. All connections come from our one hosted website.

  1. Choose a connection

    Open the connection details of the website app, or choose MCP Anything management.

  2. Add it to your assistant

    Copy its address and follow the setup instructions for your compatible assistant.

  3. Authorize access

    Sign in and approve access to your own apps and tasks. The available connection options depend on your assistant.

Equal controls for agents

Your agent is your assistant when it acts for you. Everything you can do in MCP Anything must also be possible through your agent. For example, you can create a Canvas app yourself, or you can ask your agent to create it with the same details. Both paths must give the same information and respect the same permissions. This rule covers actions and information, not the screen layout or moving between tabs.

The rule applies to app management, task teaching, testing, connections, progress, and recovery as those features become available. We check both paths before we call a feature complete. Today, the local workspace has no agent connection, so its current actions still need their matching agent controls.

You still control personal verification

Your agent could start a teaching session and give you a secure browser link. You could demonstrate the task there, or let an authorized agent operate the same session where this is supported. You still approve Duo on your phone and complete any other personal verification. After that, your agent checks progress and continues the supported work. Keep passwords and verification codes out of assistant messages.

Recovering an expired sign-in

A saved login can expire, and your task then needs a new sign-in. This is the planned recovery experience.

  1. The browser attempts sign-in

    If you chose to save your sign-in details securely, Browser Use enters them and continues as far as possible. If not, you sign in through a secure browser link.

  2. Your assistant shows a verification request

    The tool gives a Verification required status and a link that your assistant can show you.

  3. You complete verification

    Enter a verification code on the secure page, or approve Duo on your phone. Keep passwords and verification codes out of assistant messages.

  4. The task continues

    The browser finishes sign-in, and the app tries to continue the waiting task. Some assistants may need to check the task status before they show the result.

Needs a real school test

The sign-in rules of a school may prevent parts of this flow. We have not tested automatic sign-in or Duo recovery on the website of your school.

Questions that need proof

  • A recording must contain enough information to repeat the task with different inputs.
  • Some website messages may work only inside the original browser.
  • A changed website may need another recording.
  • We must measure speed before we say the product is faster.
  • The first milestone only reads information. Actions that change website data need a separate plan.

Our first build milestone

First, we teach one reading task, repeat it with different inputs, and check the result against the website. Then we run that tool from an assistant and repeat the same process on a second website.

Make failures useful

Sentry is a service that reports errors and slow steps in an app. We plan to use its error reports, Tracing, and Logs to find failed or slow tasks. The demonstration should show a real problem that these tools helped us fix.
