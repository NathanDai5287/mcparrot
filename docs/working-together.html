Share the picture before we build.

This page explains how you and the coding agents reach the same understanding of a change before anyone builds it. You explain what you expect, and we test that understanding together until we mean the same thing.

How a conversation works

  1. You describe your mental model

    Explain what you see, what you do, and what you expect to happen next. Start with a real situation, such as creating a Canvas tool.

  2. The agent explains its understanding

    The agent repeats the flow in plain language from your point of view. It keeps your decisions apart from its own assumptions and from things that need testing.

  3. We question the details

    Both sides challenge unclear steps, hidden assumptions, and failure cases. We use concrete examples to find where our expectations differ.

  4. We close the differences

    We revise the explanation until we share the same picture. An unknown technical limit stays marked as unknown until a test gives evidence.

  5. We record the agreement

    Before it builds the agreed change, the agent updates the product guide, the hackathon guide when it applies, and its own working instructions.

  6. We build and check the result

    We test the result against the agreed example. If new evidence changes the expected experience, it starts another focused discussion.

An example conversation

Example

You: “I perform the task, and the app records the requests.”

Agent: “You demonstrate each task during teaching. Your assistant later repeats the saved requests.”

Next question: “What happens when the login expires?”

In this example, the last question makes us decide how sign-in recovery works before we build it. If we only agreed on the words “browser automation,” too much would stay unexplained.

Checks before we build

  • We can both explain the starting point, user actions, and expected result.
  • We know who does each step: you, the app, or your assistant.
  • We can explain the same action through the website and through your agent.
  • Both paths give the same results and respect the same permissions and personal verification.
  • We have named important interruptions, such as verification or a failed task.
  • We have kept agreed behavior apart from questions about what is possible.
  • We have recorded the smallest next step that can test the plan.

The agent continues settled work without asking you to approve the same choice again. We check both website and agent access before we mark a feature shipped. If evidence changes the plan, the agent explains the effect and returns to the specific open question.

Saving and sharing changes

When an agent finishes a change and checks it, the agent saves it straight into the main copy of the project on GitHub, the website that stores the project and its history. The agent does not ask you first. Before it saves, it tests the change in a way that fits the risk, and it runs the project's automatic checks. Each saved step is small and has a short note that says what changed for the user. Agents never save passwords, keys, sign-in data, or private website content.

The main copy must always be ready for a demo, because judges can see it and the demo runs from it. For riskier work, an agent uses a branch, which is a separate copy where it can work without changing the main copy. When the work is ready, the agent opens a pull request, which is a request to move the branch's changes into the main copy after a review. Agents use a branch and a pull request in these cases:

  • Several agents work at the same time on the same part of the project. Each agent gets its own branch, but agents that work on clearly separate parts can save to the main copy.
  • The work is an experiment that we may throw away, such as a first test of recording and repeating website requests.
  • The change is something you can see on screen, and you should see it before it reaches the main copy. Its pull request shows pictures from before and after the change.
  • The work happens in the final hours before the Devpost submission or during in-person judging, when the main copy must not change unexpectedly. The LA Hacks 2026 guide has the deadline and event details.

Agents decide when to merge their own pull requests into the main copy. They merge after the automatic checks pass and they have confirmed that the result works, so you do not need to approve. After each change, the agent gives you a link to the saved change or its pull request.

Automatic publishing is connected

Each update to the main copy automatically publishes to the production website. Each branch also receives a preview link, which is a separate web address that shows that version of the app. You can review changes there without starting the app on your computer. After each update, the agent checks the live website, sends you its link, and fixes or undoes a broken update immediately. These guides remain separate from the hosted website.

Guides and their readers

The project has two kinds of documents that describe the same decisions. You read these web guides, which explain the experience, decisions, current status, and open questions in plain language. The product guide covers what MCParrot does, the LA Hacks 2026 guide covers judging and prizes, and this page covers how we work together. The status page is the one place that shows what is shipped, dormant, aspirational, or a gap. The coding agents read separate text documents with the same facts plus working rules, requirements, technical details, and checks. When a decision changes, the agent updates both kinds, and every document marks a feature as aspirational until a passing check makes it shipped.

The documentation rules say how all of these documents are written.
